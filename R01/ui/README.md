# UI 与战斗信息设计 · 第一轮

三张 1280×720 PNG 为 **概念合成图，未接入 Godot，非实机截图**。三套共用角色坐标、取景、血量、技能与状态数值，便于用户只比较美术方向；画面数值是独立示例，不声称是同一次真实模拟结果。

## 方案比较

|方向|优点|成本与风险|建议|
|---|---|---|---|
|A 暖色玩具街机|暖黄鸭与紫兔轮廓清晰；浅色木质边界亲切，适合轻松竞技；状态颜色对比直观|易显得轻量，需靠精致动画建立打击感|优先：形成角色识别度后扩展|
|B 暮色锻造工坊|火花、锻造与雷电有环境动机；深色场景更突出特效|兔子与环境紫褐色接近，特效密集时需加强外轮廓|适合希望战斗更有重量的选择|
|C 青紫霓虹竞技|高对比信息层，适合竞技气质；矩形网格和霓虹边界统一|雷电、冷却与装饰容易争抢青色，必须降低背景亮度|适合更强调状态读取的选择|

## 布局原则

- 顶栏固定展示双方名称、数值血量与长血条，避免角色重叠时信息一起遮挡。
- 场内只突出当前威胁：雷云持有者、剩余秒数，以及兔子已蓄伤害；持有者用云位置、闪电和数值共同编码。
- 兔子的 `stored_damage` 持续累积且代码未设上限，所以使用数值，不画“充满百分比”槽；`forge` 是2秒定身锻造状态，不代表蓄伤从零到满。
- 底栏四格是自动技能状态展示，不是可点击操作按钮。示意冷却仅显示秒数/READY，避免用户误以为需要点击。
- 这是16:9横屏概念。手机缩放可读性、刘海安全区、竖屏替代布局尚未验证；正式接入时应按安全区域处理，最小文字不能直接按整图缩小。

## HUD 字段与事件映射

|概念字段|现有来源|更新规则／注意事项|
|---|---|---|
|生命值与血条|`Fighter.health / max_health`|受伤后同步；归一化只用于血条，数值同时呈现|
|技能1/2剩余秒数|`Fighter.cd_one / cd_two`|`<=0` 显示 READY；冷却归零后可能立即自动触发，READY不是持久状态|
|雷云位置／持有者|`UnluckyDuck.cloud_holder`|碰撞切换所有者；转移演出不能延迟真实持有状态|
|雷云倒计时|`UnluckyDuck.storm_left`|初始7秒；计时技能按持有者增加或减少2秒，因此不要把倒计时条固定解释成0–7的普通冷却|
|落雷警示|`strike()`，`lightning_flash`|0.25秒现有闪光；32伤害或被半径100内避雷针吸收；保护分支须区别反馈|
|已蓄伤害|`ForgeRabbit.stored_damage`|每秒基础+8，forge状态1.5倍；碰撞释放并归零；没有固定蓄满值|
|锻造状态|`action == "forge"`、`action_left`|2秒定身；UI不能暗示必定2秒后自动重击，伤害在后续接触敌方时释放|
|淬火状态|`temper_left > 0`|3秒窗口，碰撞伤害1.5倍；建议额外边框和文字“淬火”，不只靠颜色|
